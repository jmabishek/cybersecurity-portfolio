While browsing normally and watching online content, Wireshark captured a very large amount of traffic.

The important lesson was that normal computers constantly generate network traffic from many different sources.

For example:

```text
Browser
   │
   ├── Web traffic
   ├── DNS traffic
   ├── Encrypted connections
   └── Multiple servers

Operating System
   │
   ├── Background services
   ├── Network discovery
   └── Other connections

Other Applications
   │
   └── Their own network traffic
```

This means that simply starting Wireshark can quickly produce thousands of packets.

The challenge becomes:

```text
Large Capture
     │
     ▼
Remove unrelated traffic
     │
     ▼
Focus on one protocol,
host or conversation
```

# 03 — 🔎 Display Filters Became More Important

Today I understood why Wireshark display filters are so useful.

Without filtering:

```text
Thousands of Packets
████████████████████████████████████
```

With filtering:

```text
Thousands of Packets
        │
        ▼
Apply Filter
        │
        ▼
Relevant Packets
█████
```

A display filter does not delete the other captured packets.

It only changes:

```text
what Wireshark displays
```

The original capture still contains the other traffic.

# 10 — 🌊 What I Learned About a Stream

While filtering conversations, I repeatedly encountered Wireshark's:

```text
stream
```

field.

For example, Wireshark may assign a stream number to packets belonging to a particular TCP or UDP conversation.

Conceptually:

```text
Entire Capture
     │
     ├── Conversation 1
     ├── Conversation 2
     ├── Conversation 3
     └── Conversation 4
```

Wireshark can internally number these conversations so I can isolate one of them.

Example:

```text
udp.stream eq 33
```

means:

> Show the UDP packets that Wireshark has grouped into UDP stream 33.

The number:

```text
33
```

does **not** mean:

```text
Video number 33
```

or:

```text
Application number 33
```

It is simply a Wireshark stream identifier for that captured traffic.

This was an important correction in my understanding.

```text
        │
```

This makes packet investigation much more manageable.

# 16 — ⚠️ What a DNS Hostname Does NOT Automatically Prove

This was an important investigation lesson.

If I see:

```text
googlevideo.com
```

inside DNS traffic, I should not immediately conclude:

```text
"The user definitely watched a YouTube video."
```

That conclusion is too strong based only on one DNS hostname.

The correct way for me to think about it is:

```text
Captured Evidence
      │
      ▼
googlevideo.com hostname observed
in DNS traffic
```

That tells me what I actually observed.

It does not automatically tell me the complete user activity that caused it.

This helped me understand an important cybersecurity principle:

> **Observation and conclusion are not the same thing.**

I should report what the evidence supports instead of assuming more than the packets actually show.

# 20 — 🛡️ Why This Matters for Cybersecurity

Packet captures can contain huge amounts of information.

A security analyst cannot realistically inspect every packet manually.

The useful skill is being able to reduce the capture.

For example:

```text
Large Capture
     │
     ▼

     │
     ▼
Host / Conversation
     │
     ▼
Small Relevant Dataset
     │
     ▼
```

```text
Network troubleshooting

Incident investigation

Suspicious connections

DNS investigation

SOC investigations
```

My current focus is building the fundamentals first rather than trying to identify attacks before I can confidently understand normal traffic.
